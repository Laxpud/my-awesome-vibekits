# 代码注释审查与改进

帮助具备编程基础、但不了解当前实现及隐含约定的读者，顺着注释理解代码的作用和处理过程。日常编码习惯由用户及项目规则约定；本技能用于有明确目标范围的注释审查、补全与整改。

## 确定任务边界

- **审查**：报告妨碍理解的具体位置、缺失信息及改进方向，必要时给少量改写示例；不因发现问题直接编辑文件。
- **补全或整改**：用户已要求执行时，直接修改授权范围内的注释和说明性 docstring，保持可执行代码与行为；不把已获授权的整改退回成再次请示。若用户同时授权功能修改，代码变更遵循该功能任务的范围。
- 保留工具会解析的指令注释、构建标记等内容；docstring 若被运行时代码读取，也需保持其使用契约。发现代码缺陷时指出问题，不借注释整改实施无关修复。

## 理解代码并定位阅读障碍

1. **确认整体任务。** 阅读目标函数或模块的完整逻辑单元，沿必要的调用、类型、配置和数据来源补足上下文。阅读范围随语义依赖扩大，不默认通读整个仓库。旧注释只作为线索，含义应由代码或已确认资料支持。
2. **梳理处理过程。** 沿输入到输出找出主要阶段及重要子步骤，检查读者能否知道当前处理什么、发生什么变化、结果如何衔接。实现简单的操作也可以需要流程路标；长代码块内部包含不同动作时，继续拆解说明。
3. **找出理解缺口。** 重点识别没有交代任务的技术结论、对象不明的抽象词、缺少中间环节的因果、未说明的数据约定，以及与实现不符的描述。不要只按注释条数、代码复杂度或是否解释了原因判断质量。

## 选择说明位置并改写

按读者需要选择层级，不为每个符号机械补满字段：

| 位置 | 需要说明的内容 |
| --- | --- |
| 文件或模块概述 | 承担哪段工作，必要的输入、输出及使用方式；与作者、日期等身份信息模板分开处理。 |
| 函数、类及公共 API | 整体作用，参数和结果的实际含义，以及适用的副作用、异常或调用限制；避免重复签名已清楚表达的内容。 |
| 连续代码块及内部子步骤 | 具体对象、处理动作、结果与前后步骤的关系；顺序明确的流程用编号帮助扫描。 |
| 变量、表达式或配置旁 | 数据字段、shape、单位、坐标或状态约定、参数影响及局部边界；较长解释放在对应操作上方。 |

改写时先交代对象、动作和结果，再补必要的原理、原因与约束。用通俗、指称明确的句子，把公式符号、代码变量和计算用途联系起来；不要用术语堆砌或孤立的设计不变量代替过程说明。

例如，已知 `data` 两列分别是接收时间（s）和声压（Pa），要提取 `[start_s, end_s]` 内的记录：

```python
# 1. 提取接收时间列，用于判断每个采样点是否落在指定时间窗内。
time_s = data[:, 0]

# 2. 同时保留时间和声压两列，得到指定时间窗内的完整记录。
in_window = (time_s >= start_s) & (time_s <= end_s)
window_data = data[in_window]
```

代码虽然简短，注释仍能交代数据含义和处理步骤。说明的对象是领域操作，避免逐行翻译赋值、循环等语法。

需要校准表达尺度时，按当前问题阅读[正反例与改写理由](references/comment-examples.md)中的对应主题：流程粒度、对象与资源流程、因果衔接、数据与公式、注释真实性。无需为一次局部改写加载全部案例，也不照搬案例中的项目约定。

沿用用户和项目适用的语言及文档格式；未指定时，解释性文字默认中文，代码标识符、公式和协议字段保留原文。保留可用的排版习惯，同时修正难懂的表达。用途说明按需要添加；作者、日期及 TODO 的负责人、期限等信息，仅在已有要求和可靠来源时填写，不自动推定或补造。

## 复核与交付

- 扫描整体说明和步骤注释，能否还原主要处理过程？只有笼统标题或零散注意事项时，补足中间步骤。
- 对象、术语和因果能否在当前位置或必要上下文中找到含义？公式、切片和参数说明能否与相邻操作对应？
- 对照代码核实每个步骤、条件、阈值和后果；不把假设、未经确认的数学性质或未实现行为写成事实，不写入秘密或敏感值。
- 确认改动符合任务边界，保留有语义作用的注释和文档内容。按实际改动执行必要的现有检查，区分内容审阅与运行验证，不把预计效果写成已验证结果。

审查交付应给出位置、具体阅读障碍、代码依据和改进方向，合并同类问题；没有实质问题时直接说明。整改交付应概括主要改善、实际检查及剩余不确定性，不为一次注释任务附加无关报告或全仓整理。
