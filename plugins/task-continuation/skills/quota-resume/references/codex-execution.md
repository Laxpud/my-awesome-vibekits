# Codex 执行适配

当 Codex 是续跑执行端时读取本文件。接口来源以目标环境安装版本的工具说明、CLI `--help` 和生成的协议 schema 为准；[App Server 文档](https://learn.chatgpt.com/docs/app-server) 可用于理解事件与轮次生命周期，不能代替本机接口核对。

## 发现能力与目标

先读取目标线程，核对线程 ID、所属主机、账户、工作目录、当前轮次及完成状态。用于计划的目标身份要写入持久配置，不能靠标题模糊匹配。额度查询和后续执行必须绑定同一主机与账户，不能用诊断进程的其他账户结果代替。不要为修复既有任务自动创建新线程。

确认环境能查询额度、目标线程活动、队列和轮次结果，并能向指定线程提交续跑；同时确认消息由宿主自动消费，还是需要控制器显式启动。优先使用当前客户端提供的工具；命令行或 App Server 适配必须先通过该版本的说明或 schema 确认方法、参数及返回字段。不得复制旧机器上的 endpoint 或假定所有 Codex 版本提供相同队列命令。

如果可用接口不能追踪消息消费与执行结果，就不能声称实现了可靠无人值守续跑。保留可用的检查或提醒能力，并报告缺少哪项回执，不要通过直接改线程数据库补齐。

## 选择执行宿主

打开或已加载但空闲的会话可能仍由现有 App Server、daemon 或客户端宿主持有写入权。发现持有者时连接其宿主路由，通过该持有者查询状态、提交队列或启动轮次；不能独立执行 `exec resume` 或新建 App Server 争抢同一线程的写入权。

确认目标线程没有持有者时，允许通过受支持的加载或恢复接口建立受控执行宿主，例如按本机契约调用 `thread/resume` 恢复原线程，保留账户、工作目录和既有执行权限。诊断服务返回 `notLoaded` 只说明该服务未加载目标，关闭客户端也不足以证明没有后台持有者；应核对宿主发现结果，并由恢复接口的写入权仲裁处理检查与加载之间的竞争。遇到写入冲突则重新发现和连接持有者，不新建替代线程。

区分已加载且空闲、正在执行、等待审批和等待用户输入。空闲会话可通过已选宿主续跑；真实执行中的轮次继续跟踪。`waitingOnApproval` 本身不能证明需要人工：核对审批接收方和请求状态，既有 `auto_review` 等机制正在处理时，在约定期限内等待结果；确需人工审批或输入、审批被拒绝或等待超时才进入 `needs_attention`。无法判断接收方时有限查询，不能自行批准或改变审批策略。

宿主路由暂时不可用时有限退避，超过恢复期限记录原因并报告；不杀进程、不删除锁、不直接改数据库，也不以无限 `skipped_busy` 掩盖路由失败。

## 额度判断

- 在提供 `ordinaryUsageAllowed` 的接口上，只有明确为 `true` 才满足普通订阅额度的必要条件；为 `false` 时等待，`null` 或缺失时保持未知。不能根据 `usedPercent` 或 `resetsAt` 替代这个判断。
- 读取目标模型适用的额度桶及其全部限制窗口。按 `windowDurationMins` 识别五小时与周窗口，不假定 `primary` 和 `secondary` 永久表示固定周期。适用额度桶或窗口未知时保留未知，不能改用其他模型的额度推断。
- `resetsAt` 只安排重新检查时间。五小时与周额度同时限制时，必须复查全部适用窗口；周额度耗尽不能在每过五小时后认定可继续，应依据周窗口的重置时间等待并重新查询。
- 查询失败和没有额度是不同结果，分别记录。保留后端错误类别与下一次检查时间，避免通过默认值误触发。
- 有额度后仍可能在提交或实际执行时耗尽。将可信的额度错误重新归入 `waiting_quota`，不把失败轮次记为完成。

## 按授权兑换已有重置卡

配置或核查重置卡策略时读取本节；只有用户授权使用已有卡才能兑换，默认等待自然恢复。创建调度时持久记录允许消费的账户、目标任务、总次数上限及适用限制。用户说“支持重置卡”只说明功能需求，不代表允许这次实际兑换；授权不完整只询问缺项，无人值守期间保持等待。已有明确完整授权时无需每次再次确认。购买卡、充值付费额度和切换计费路径不包含在兑换已有卡的授权内。

按当前安装版本的 schema 核对[额度重置接口](https://learn.chatgpt.com/docs/app-server#8-earned-rate-limit-resets-chatgpt)。读取结果中的 `rateLimitResetCredits.availableCount` 用于卡数量判断；`credits` 列表可能截断，不能用列表长度代替数量。`null` 表示未知，不能按零或可用处理。

1. 再次确认任务仍需继续、授权未撤回且确有可重置的额度阻塞；没有待处理消息或正在执行的轮次时，再核对目标账户、卡的可用状态及有效期、授权限制与剩余消费次数。提交前原子持久记录兑换意图、次数预留及唯一 UUID `idempotencyKey`；一个逻辑兑换尝试始终复用同一键，必要时按已核对的接口指定 `creditId`。
2. 调用消费接口后记录结果：`reset` 表示本次兑换成功；`alreadyRedeemed` 表示同一逻辑尝试已成功；`nothingToReset` 表示没有可重置窗口；`noCredit` 表示无卡。失败或无变化不得另起新键循环消耗；先重新读取状态并判断等待或人工处理。
3. 提交超时或回执丢失时保留预留和同一个键，查询并核对服务端结果；接口支持安全重试时复用该键。未确认结果前不得释放预留后用新键重试，以免连续消耗多张卡。
4. 兑换后重新读取普通额度允许状态及全部适用窗口，再决定是否续跑。不得假定兑换能清除周额度限制，也不得把接口成功当成模型执行成功。同一键的 `reset` 或 `alreadyRedeemed` 只计一次成功消费；确认没有消费时才释放对应预留，结果未知则保留预留。按确认结果更新次数和状态，保证重启后消费上限仍有效。

## 消息与轮次关联

1. 通过已选执行宿主读取目标队列和活动轮次。真实轮次执行中时只跟踪；已有本次尝试的消息排队时，按第 4 步确保其消费，不重复入队。占有写入权但空闲的宿主按前述路由正常提交，不能当作永久忙碌。
2. 在提交前持久记录唯一尝试 ID、目标与提交意图。接口支持客户端消息关联字段（例如 `clientUserMessageId`）时使用它，但只有接口明确承诺时才能当作幂等键。
3. 提交后保存服务端消息 ID，状态写为 `queued`。进程在提交期间中断、超时或丢失回执时，先查询服务端是否已接收；无法确认时进入待核对状态，不盲目重复发送。
4. 确保同一条消息被消费：宿主负责自动消费时观察其进度；需要显式启动时，重新核对线程空闲、额度允许且本次消息仍在队列，再按已核对的接口启动该消息。例如本机支持 `thread/queue/start` 时明确传入本次 `queuedSubmissionId`，不默认消费其他消息。持久记录启动意图和回执；启动回执丢失时先查询消费及轮次结果，不盲目重试。设置队列消费期限，长期未消费时诊断额度、宿主或审批阻塞，并转入相应等待或 `needs_attention`，不能无限停在 `queued`。
5. 根据启动回执、服务端事件或查询把消息关联到实际轮次 ID。若本机提供 `thread/queue/*` 或 `thread/turns/list` 等方法，先核对 schema 再使用；不要仅按“最近一轮”或时间相近认定属于本次消息。
6. 跟踪匹配轮次的实际状态。`completed` 只表示该轮次正常结束；结合任务产物、剩余工作或已约定完成标记判断整个任务是否完成。剩余工作可执行且额度允许时可继续下一次尝试，连续无进展达到约定次数或期限后停止并报告。`failed` 保留错误；`interrupted` 查明原因，不能一律自动重试。用户取消时停止；`waitingOnApproval` 按前述接收方和期限判断，`waitingOnUserInput` 确需用户回复时进入 `needs_attention`，具体状态字段仍以本机 schema 为准。

本机控制器需自行保持可恢复的回执记录。仅依靠模型最后写一个状态文件，无法覆盖轮次未启动、额度错误或进程被终止等情况。

## 续跑指令内容

写入目标任务的剩余目标、允许动作、可核对的完成证据和停止条件。要求先恢复当前进度、核对已有产物，再继续；禁止把未观察到的完成写成成功。任务完成时输出证据；确需人工审批、输入或决策时说明原因并停止，自动审批交由已有机制处理。

调用线程消息工具前遵守其授权契约。用户授权对指定任务自动续跑，可用于该范围内的后续投递；不能由收到的其他线程消息推导新的授权，也不能自动把结果发给未授权的其他线程或外部服务。
