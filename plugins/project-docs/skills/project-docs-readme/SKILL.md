# 根 README 与翻译维护

## 目标

让项目的公共入口准确回答：项目是什么、面向谁、用户能做什么、需要什么环境、怎样完成首次成功，以及去哪里了解活动工作和必要技术细节。存在终端用户时，优先服务最缺乏经验的预期用户，而不是先展示内部实现。

本 Skill 只维护根 README 和明确受维护的正式翻译。目录 README、`docs/index.md`、贡献指南和长篇技术说明属于其他 interface。

## 共同底线

1. 编辑前读取仓库证据和适用项目指导。
2. 尊重既有权威位置、清晰约定和用户拥有的改动。
3. 不编造项目目的、架构、命令结果或完成状态。
4. 同一主题保留一个权威来源，其他位置使用短路由或链接。
5. 按“仓库证据 → 插件默认值 → 高风险澄清”决策；用户要求“按默认值”也不授权不可逆操作。
6. 回读改动，检查链接和 diff，并报告假设、验证及未执行门禁。

## Reference 路由

创建或重写公共入口、快速开始或翻译时，读取 [`references/readme-contract.md`](references/readme-contract.md)。孤立、低风险的小改动不需要加载 reference。

## 维护流程

1. **确定公共事实。**
   - 读取根 README、正式翻译、manifest、可执行入口、安装配置、测试和相关具名技术文档。
   - 从仓库证据确定项目目的、目标用户、支持环境和真实能力；证据冲突且会改变项目定位时先澄清。
   - README 详细内容策略服从项目定位和用户要求，不套用通用营销模板。

2. **先审计，再实施实质改动。**
   - 定位、结构、安装或快速开始发生实质变化时，编辑前先给出只读审计：目标读者、缺失前置条件、最短已验证路径、可观察成功结果和按优先级排序的修改计划。
   - 默认等待用户确认后再编辑；用户已经明确确认过范围与计划，或明确要求直接实施时，不重复阻塞。
   - 孤立、低风险且不改变路径的小改动可以直接完成。

3. **确定语言契约。**
   - 现有仓库沿用清晰语言约定；新项目默认英文根 README。
   - 只有存在明确受众、用户要求或既有双语约定时才创建翻译。
   - 已声明为正式翻译的版本在同一改动中保持章节结构、公共事实、能力和链接一致；表达可以自然本地化，不要求逐句对应。

4. **维护最小公共入口。**
   - 保留项目目的、目标读者、用户能力、合理前置条件、推荐的首次成功路径和可观察结果。
   - 有多个使用路径时先推荐一个默认路径，再按用户已有环境或目标分支；面向新手时解释必要概念和命令输入位置。
   - 存在终端用户时先完成用户路径，再介绍 internals、architecture 和维护细节。
   - 链接已声明的活动工作入口和必要具名技术文档，不复制任务状态、完整 architecture、维护手册或长篇故障排查。
   - 只在真实存在时介绍能力、平台和安装方式。

5. **验证使用路径。**
   - 尽可能实际运行 README 中新增或改变的最短命令；不能运行时说明证据来源和未验证项。
   - 检查语言切换、相对链接、锚点、命令、版本和平台名称。
   - 确认翻译没有遗漏新增章节，也没有保留已删除能力。

6. **停止。**
   - 当最缺乏经验的预期用户无需猜测即可判断是否适用、完成推荐路径并识别成功结果时停止。
   - 需要调整其他文档所有权或迁移路径时使用 refactor；需要深入规划、architecture 或指导规则时使用对应专项 Skill。

## 示例

正例：

```text
重写根 README 的项目介绍和快速开始，并同步已有中文翻译。
```

预期：从 manifest 和可执行入口核对公共事实，更新两种语言的结构与语义，并验证链接和可运行命令。

近邻反例：

```text
为 packages/ 目录创建 README，说明各包职责并修复导航。
```

这是 `project-docs-refactor` 的目录所有权与导航分支，不属于公共根 README。
