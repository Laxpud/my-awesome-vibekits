# 架构与技术文档规范

默认入口 `docs/tech/index.md`，总览 `docs/tech/architecture.md`，必要时增加主题页。已有清晰路径可沿用，小项目可在一页内用锚点分层。不按文件数量自动生成一套页面。

## 事实依据与更新节点

- 按本次范围读取相关代码、配置和现有技术入口，用实际实现支撑说明，不因文档任务通读全仓库。默认记录最近核对过的当前实现；spec 用于理解意图，不能把未实施规格写成当前行为。发现实质差异时指出或作为待处理任务，不擅改 spec 或源码；用户要求目标架构时明确标为目标，与当前状态分开。
- 在里程碑收尾、已计划的中途节点或发布节点核对受影响内容，并核对 TODO 中的文档同步条目；没有 TODO 时不为此创建。普通代码任务完成不自动触发全篇同步，没有变化不改正文，直接阻碍当前工作的错误及时修复。
- 技术入口标明最近核对的里程碑或版本，有 TODO 后续工作时链接过去，不逐任务追加过期提醒。已实现并核对的代码不因尚未发布被写成未来状态。
- 交付前检查本次修改的图和说明是否符合代码、是否可读；可用时渲染改动图，无法渲染说明限制。不重验未改图，不另建技术文档验收报告。

## 从整体到局部

采用 C4 本身，按项目规模选择需要的层级：

| 层级 | 回答的问题 |
| --- | --- |
| L1 系统上下文 | 谁使用系统，系统与哪些外部系统交互？ |
| L2 容器 | 哪些应用、进程、服务或数据存储协作？这里的容器不是源码目录或 Docker 的同义词。 |
| L3 组件 | 一个容器内部有哪些有职责边界的组件，怎样协作？ |
| L4 代码（可选） | 关键复杂实现内部怎样组织？仅在确有理解价值时展开。 |

组件页附近另设源码映射，覆盖自有生产代码文件和关键脚本，让读者找得到每个文件的归属。普通辅助文件可按职责分组列出，文字无需逐一解释；测试按被测模块分组，生成代码、第三方代码只标边界。源码映射不是强制 L4，也不等于把所有文件、import 和调用放进一张图。

图先展示关系，短文补充原因、约束、例外和不能由图表达的行为。按需要说明输入输出、主要处理过程、关键算法、失败处理和工程假设；公式和完整字段说明放在确实需要的主题页，不把所有细节挤入总览。

## 图与链接

默认用 Mermaid 常见语法表达 C4 语义，不强制特殊 C4 扩展语法或新工具依赖。每图回答一个问题；节点过多就拆图，流程和时序有助理解时另画。标注关系是调用、数据传递、依赖还是包含，避免混在一起；图未画出的依赖不代表不存在。

入口链接总览，总览链接容器或组件主题；主题页返回上层，并按需要链接相关主题。图旁提供可点击的源码与下层文档链接，不依赖平台对图内链接的支持。无需每页互链所有文档。

开发依赖说明用途、依赖关系与必要版本；不写通用依赖安装教程。目录树只作为导航，不能代替关系解释。

## 内容边界

技术文档承载当前机理和长期约定；TODO 承载状态；plan/spec 保留 agent 原文；ADR 承载必要的决定理由。避免在多个位置维护相同事实。目录 README 不自动生成；已有目录说明的取舍见[目录 README](readme-directory-rules.md)。
