# 项目文档结构重构

## 目标与模式

让已有文档形成少量清晰入口和唯一权威来源，同时保留仍然有效的内容、用户改动和外部链接价值。

按用户请求选择模式：

- `audit`、`review`、`评估`：只读盘点并报告问题与建议，不移动或改写文件。
- `refactor`、`reorganize`、`重构`、`整理`：完成盘点后直接实施低风险、范围内的结构变更；高影响迁移仍应用澄清门槛。

只有在没有安全、可逆默认值，且选择会改变可能公开的路径、活动工作或决策历史的权威来源、公共承诺，或删除无法证明已迁移的内容时，才因高影响暂停澄清。可用 redirect note、保留原文或明确仓库证据控制风险时，按默认值继续并记录判断。

单一文档的内容维护优先使用专项 Skill。Refactor 可以为确立权威来源、消除重复和纠正迁移后的过期表述而改写，但不接管深入的 README、planning、architecture 或 guidance 语义。

## 共同底线

1. 编辑前读取仓库证据和适用项目指导。
2. 尊重既有权威位置、清晰约定和用户拥有的改动。
3. 不编造项目目的、架构、命令结果或完成状态。
4. 同一主题保留一个权威来源，其他位置使用短路由或链接。
5. 按“仓库证据 → 插件默认值 → 高风险澄清”决策；用户要求“按默认值”也不授权不可逆操作。
6. 回读改动，检查链接和 diff，并报告假设、验证及未执行门禁。

## Reference 路由

- 文档分散、重复、过期、冲突或需要移动时，读取 [`references/reorganizing-docs.md`](references/reorganizing-docs.md)。
- 创建、删除、移动或重新定义目录 README 时，读取 [`references/directory-readmes.md`](references/directory-readmes.md)。

只读取当前分支需要的 reference。

## 默认所有权

仓库已有清晰约定时沿用；没有约定时采用以下 fallback：

- 根 README：面向用户的目的、能力、环境和最短已验证路径。
- 已声明的活动工作入口：方向、承诺、tasks、退出条件和完成证据。
- `docs/` 下具名文档：架构、设计、数据契约、配置、测试和其他稳定技术细节。
- Agent 指导文件：文档与代码路由、工作流触发器和少量高风险边界。

新项目需要技术索引时默认 `docs/index.md`。现有有效的 `docs/README.md` 不是天然错误，不因命名偏好重命名。

## 重构流程

1. **建立完整盘点。**
   - 读取文档内容而不是只看文件名，并检查 README、规划入口、`docs/`、项目指导文件、manifest、关键源码和 Git 状态。
   - 标记每份文档的受众、主题、当前或历史状态、入站链接以及是否包含未解决工作。
   - 判断仓库是缺少基线还是已有基线失序：只有占位材料且没有能表达目的与入口的公共文档时改用 bootstrap；已有非占位公共入口但部分内容缺失、重复或失序时继续 refactor。

2. **确定权威来源。**
   - 为每个重复主题选择一个证据最强、维护路径最清晰的位置。
   - 内容冲突且证据不足以判断时，不静默选择；高影响冲突先澄清，低影响不确定性明确记录。
   - 用短路由或链接替代副本，避免在 README、规划、architecture 和指导文件间复制规则。

3. **设计最小目标结构。**
   - 保留清晰、稳定的现有约定；只有现状造成发现、所有权或维护问题时才迁移。
   - 多份技术文档确实需要导航时才保留索引。
   - 目录 README 只有在稳定但不直观的局部职责、多个子区域、公共入口或修改风险存在时才保留或创建。
   - 不把所有目录和所有文件变成文档节点。

4. **实施迁移和必要改写。**
   - 尽量使用能保留 Git 历史的移动。
   - 更新受影响链接、索引和短路由，并改写因位置或权威变化而过期的措辞。
   - 内部引用能够完整更新时直接迁移；旧路径可能被外部引用时保留简短 redirect note。
   - 未解决工作先迁入活动规划入口或明确 backlog；不能通过归档或删除隐藏。
   - 深入改变公共 README、规划模型、architecture 或 agent 规则时，追加对应专项 Skill。

5. **验证可发现性和停止线。**
   - 搜索旧路径、重复定义、断链、已删除草稿引用和会解析到意外 README 的目录链接。
   - 回读全部修改文档，确认每个主题只有一个权威来源，活动工作和历史记录没有混淆。
   - 检查 Git diff 只包含请求范围内的文档重构；结构清晰后停止，不借机全面重写内容。

## 示例

正例：

```text
审查这个仓库的 README、TODO 和 docs，找出重复内容；先只给我重构建议。
```

预期：使用 audit 模式盘点权威来源、冲突、旧路径和建议结构，不编辑文件。

近邻反例：

```text
更新根 README 的安装步骤，并同步正式中文翻译。
```

这是 `project-docs-readme`；文件之间存在翻译同步不等于文档结构重构。

组合示例：

```text
把散落的 roadmap 和 milestone 文件重组到一个清晰入口，并重新设计 active work 规则。
```

以 refactor 负责位置、所有权、迁移和链接；规划概念与执行契约由 `project-docs-planning` 深化。
