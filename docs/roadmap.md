## Backlog

以下方向尚未承诺实施，待有明确需求时再确定范围，不作为当前 Codex / Claude Code 市场维护或独立 Skill 分发的默认门槛。

### 按实际需求扩展市场分发入口

- 价值：让有实际使用需求的其他客户端通过本市场发现和安装独立仓库的插件。
- 启动条件：用户明确目标客户端与安装需求后再确定范围，不预先承诺平台名单。
- 已有思路：优先复用现有 marketplace 格式与独立仓库提供的插件包；能直接复用时仅补充安装入口和说明，确需不同市场清单时再由统一 catalog 生成对应适配文件。
- 职责边界：本项目只维护市场来源、清单适配和安装入口；插件专属 manifest、技能与平台能力配置由独立仓库按需维护，独立 Skill 安装沿用其公开的分发说明。
- 检查范围：核对新增市场清单、来源映射和安装说明，沿用维护指南中的现有检查；不默认增加逐插件行为或客户端完整生命周期验证门槛，不让未来平台门禁阻塞当前两端发布。
- 待明确：目标客户端是否支持外部插件来源、能否直接复用现有市场格式，以及必要的市场字段与安装入口。

## 已取消安排

### 外部市场与客户端生命周期

**已取消（2026-10-13）**：用户明确本仓库只负责外部插件来源、收录更新和安装入口。客户端的刷新执行、启停、本地版本恢复、安装隔离和失败恢复不作为市场交付门槛；市场仍核对自己声明的来源、版本与技能清单。以下保留原规划，不作为未完成工作继续推进。

**已有结果**：独立仓库迁移、两端市场入口和快照回填已完成，见[维护里程碑归档](archive/milestone-2026-10-12-17-59-marketplace-maintenance.md)。用户已确认三个插件的 Codex 展示，以及 Codex 与 Claude Code 两端的安装、升级、卸载通过。恢复旧内容后发布更高版本仍属于升级链路，不再单列回退验证。

**原目标**：补齐外部插件在 Codex 与 Claude Code 两端市场中的客户端生命周期验证。2026-10-12 已确认保留两端支持，取消原仅支持 Codex 的收敛方向。

**原完成条件**：两端市场刷新、逐插件安装、升级、启停、卸载和独立回退均完成客户端验证；实际来源、版本与完整技能集合符合独立仓库发布内容，操作保留兄弟插件状态，失败恢复与临时资源清理明确，公开支持说明与实际验证范围一致。

**原任务清单（随里程碑取消）**：

- [ ] 验证两端市场刷新与逐插件安装，核对实际来源、版本与完整技能集合。
- [ ] 验证逐插件升级、启停、卸载和独立回退，核对兄弟插件状态、失败恢复和临时资源清理。
- [ ] 核对并同步本里程碑影响的项目文档，保持双语 README 的支持声明与实际验证范围一致。

### 外部客户端生命周期自动化

**已取消（2026-10-13）**：客户端完整生命周期验证不属于本市场职责，不继续将其自动化列为默认后续工作。以下保留原候选思路。

- 价值：减少两端市场生命周期验证中的重复操作。
- 已有思路：先完成上述客户端验证，再按需要设计外部自动化；不恢复已取消的同仓库 E2E 与日常晋级工具。
- 待明确：哪些客户端与操作适合自动化，如何处理授权、失败恢复和临时资源清理。

### 专属扩展 manifest

**已取消（2026-10-13）**：插件专属 manifest 与平台能力配置由独立插件仓库按需维护；本市场所需的 marketplace 清单适配并入 Backlog 的市场分发入口方向，不在本仓库生成插件 manifest。以下保留原候选思路，不代表已启动独立仓库的适配工作。

- 价值：通过平台适配表达通用插件格式无法覆盖的能力。
- 候选范围：Cursor Plugins、Gemini CLI extensions、Kimi Code plugins，以及未来出现稳定作者分发协议的平台。
- 已有思路：由统一 catalog 生成薄适配文件，不复制 Skills 内容；平台专属 hooks、commands、agents 和权限语义不得进入通用 `SKILL.md`。
- 待明确：哪些平台确需专属 manifest，以及具体能力和权限如何映射。

### Skills 目录与配置投影

**已取消（2026-10-13）**：不在本市场自建跨客户端的 Skill 安装器；目录安装、更新和卸载交由分发工具或客户端处理，本市场依据独立仓库公开的安装说明提供入口。以下保留原候选思路。

- 价值：为兼容 Agent Skills、采用目录或配置接入的 Harness 提供分发路径。
- 候选范围：OpenCode、TRAE、Windsurf、Qoder、Gemini CLI 及其他兼容 Agent Skills 的 Harness。
- 已有思路：安装器支持 dry-run、选择插件、幂等安装和安全卸载，只处理自身创建的路径，不覆盖用户已有同名 Skill；扁平命名空间必须检测跨插件 Skill ID 冲突。
- 待明确：各平台的发现路径、配置投影方式与目录所有权识别方式。

### 跨 Harness 验证矩阵

**已取消（2026-10-13）**：不为本市场建设覆盖各客户端的独立兼容性验证矩阵；新增市场适配时核对本项目维护的分发内容，支持声明遵守[现有检查边界](tech/architecture.md#检查能够证明什么)。以下保留原候选思路。

- 价值：区分兼容层级，让支持声明对应实际证据。
- 已有思路：按“内容兼容、插件包兼容、marketplace 分发兼容”分别记录；有可用 CLI 的平台执行自动化 smoke test，只有 schema 的平台执行静态验证，其余平台保留明确的人工验证记录和置信度。
- 待明确：首批覆盖的平台、可用验证工具和人工验证方式。
- 发布边界：不得因为 `SKILL.md` 可读取就宣称 marketplace 或生命周期完全兼容，也不得让未来平台门禁阻塞当前 Codex / Claude Code 发布。
