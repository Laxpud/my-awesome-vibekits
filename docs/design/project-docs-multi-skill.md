# Project Docs 改造设计

状态：2026-09-26 已在源码中实施七技能改造，Codex 轻量验收通过。尚未发布或更新日常安装；catalog 版本仍为 2.0.0，正式发布时另行定版。

目标：让用户不读代码也能掌握进展、理解项目，让 AI 找到下一步并沿已有讨论继续工作。默认维护现有记录，不为每次工作生成日志、验收报告或交接文档。

原六技能拆分的背景保留在 [ADR 0001](../adr/0001-split-project-docs-by-user-intent.md)。本设计替换旧目标设计中的自动路由、规划布局、文档更新和验收要求，不改写旧 ADR 的历史决定。已记录的指令审查问题见 [project-docs 审查记录](../reviews/2026-09-24-project-docs.md)。

阅读导航：[技能职责](#技能职责与调用) · [目录布局](#文档分工与默认位置) · [规划模板与归档](#规划格式与生命周期) · [技术文档](#技术文档c4源码导航与更新节点) · [README](#readme初学用户的使用入口) · [使用说明](#使用说明完成具体用户任务) · [共享写作规则](#共享写作规则) · [迁移与验收](#旧项目迁移)。

## 范围与原则

- 保留现有六个专项技能，新增一个轻量进度技能；本轮只考虑 Codex 的可用性。
- 文档格式统一，执行方式由任务决定。模板固定信息位置，不要求创建空目录、空标题或完整文档套件。
- 一个事实或任务状态只维护一处，其他位置链接过去。工作推进时移动原有内容，避免复制出多份清单。
- 保存未来会用到的方案、必要约束和真实证据，不默认保存每次操作经过。
- 不编造能力、依赖、命令结果或完成状态；不把文档维护授权扩展为源码修改、发布或全局配置修改。
- 明确的用户指令优先。已授权范围内继续执行；只有缺失信息会改变结果或触及明确权限边界时才询问。
- `npx skills` 支持和插件市场收敛为仅支持 Codex 是后续工作，见 [TODO](../../TODO.md#未来发展方向跨-harness-兼容与分发)。本次不移除现有平台适配或改变正式分发方式。

## 技能职责与调用

| 技能 | 调用方式 | 职责 |
| --- | --- | --- |
| `project-docs-progress`（新增） | 允许自动调用 | 读取活动入口，定位当前工作，维护最小进度，按既定规则链接材料和归档 |
| `project-docs-bootstrap` | 显式调用 | 初始化真实需要的最小文档与入口 |
| `project-docs-planning` | 显式调用 | 建立或调整 TODO、roadmap、milestone、backlog 的结构和约定，规定 plan/spec 的保存与归档方式 |
| `project-docs-refactor` | 显式调用 | 整理重复、过期、难读或难找的文档，完成范围内迁移和历史整理 |
| `project-docs-readme` | 显式调用 | 维护面向初学用户的 README、正式翻译、推荐使用路径和配套使用说明 |
| `project-docs-architecture` | 显式调用 | 按节点维护 C4 架构、技术说明、源码映射与必要 ADR |
| `project-docs-guidance` | 显式调用 | 维护 AGENTS 等指导文件的短路由、必要规则和权限边界 |

六个专项技能在各自 `agents/openai.yaml` 中设置：

```yaml
policy:
  allow_implicit_invocation: false
```

进度技能允许隐式调用。不能仅靠正文中的“不要自动加载”控制选择；description 仍需简短、准确地说明用途与触发条件。具体安装与调用设置按 Codex 的实际支持检查。

### 进度技能的边界

- 用户继续项目、执行已有任务或查询进度时可以触发；普通问答、解释代码、孤立的小修改不默认触发。
- 只读活动入口和当前任务需要的材料；没有入口时继续处理用户任务，不自动建立文档体系。
- 用户指定工作优先。没有指定时，从当前里程碑中选择已有焦点或按优先顺序选择可执行任务；跳过明确阻塞的任务。
- 完成情况、下一步、阻塞或关键决定实际变化时，更新已有位置。不追加会话日记，不创建总结报告，不自动加载整套专项技能。
- 可按已确定的项目规则维护链接和归档；改变规划结构、承诺或文档体系需要明确的规划或整理任务。
- 当前里程碑完成，不代表获得实施下一里程碑的授权；backlog 也不能自行提升为承诺。
- 计划内的文档同步任务可以按授权处理。专项技能改为显式调用，不禁止普通开发顺手修正直接受影响的少量事实，也不授权顺带重构文档。

## 文档分工与默认位置

```text
README.md                       公共使用入口
TODO.md                         当前里程碑与任务
AGENTS.md                       AI 工作规则与阅读路由
CLAUDE.md -> AGENTS.md           相对软链，不维护第二份指导正文
docs/
  README.cn.md                  已约定的正式中文翻译
  index.md                      确有需要时提供整体导航
  roadmap.md                    后续里程碑、backlog、已完成里程碑链接
  usage.md                      按需创建的用户使用说明
  plans/                        需要长期保留的未完成计划
  specs/                        需要长期保留的未完成规格
  tech/
    index.md                    技术阅读入口
    architecture.md             架构总览
    <主题>.md                   按需展开组件、流程或技术机制
  adr/                          少量长期重要决定
  evidence/                     必须保留的测量、验证或复现材料
  archive/                      统一存放已结束的 milestone、plan 和 spec
```

只在存在真实内容时创建对应位置。新建或明确迁移的项目采用上述布局；现有清晰路径不因名称偏好迁移。没有独立 backlog、current-plan 或 decisions 的默认文件要求；backlog 属于 roadmap，decisions 的职责由 ADR 承担。

- TODO：当前承诺、完成条件、任务勾选、必要阻塞和方案链接。
- Roadmap：方向、阶段顺序和依赖。近期里程碑可以较具体，远期只保留粗略结果；backlog 保存尚未承诺的候选工作。
- Milestone：有边界的交付结果。当前详情承载于 TODO，未来详情承载于 roadmap，完成后移入 archive。
- Plan/spec：agent 生成的可选参考材料。插件管理保存、链接和归档，不规定或维护正文。
- 使用说明：用户跑通快速开始后，怎样完成具体任务、选择常用选项和处理使用问题；不解释内部实现或复制安装说明。
- 技术文档：最近核对过的系统结构、机理和长期约定，不承载任务进度。
- ADR：重要决定及理由。Evidence：必要的原始证据。两者不因任务存在而必然创建。

## 规划格式与生命周期

### TODO 模板

模板中的路径和名称为示例，不是本仓库已有产物。方括号复选框只表达任务完成情况；可选字段没有内容时省略。

```markdown
# 当前工作

### 当前里程碑：批量导出

目标：一次处理多个输入文件。
完成条件：支持批量执行，单项失败不影响其他输入。
方案：[实施计划][plan] · [行为规格][spec]

- [x] 明确输入输出约定
- [ ] 实现批量执行
- [ ] 验证单项失败处理
- [ ] 核对并同步本里程碑影响的项目文档

### 下一个里程碑：发布准备

见 [路线图][next]。

[plan]: docs/plans/plan-2026-09-26-10-30.md
[spec]: docs/specs/spec-2026-09-26-10-35.md
[next]: docs/roadmap.md#发布准备
```

- 目标与完成条件是里程碑的必要内容；完成条件较多时分条表达，不复制 spec 的全部场景。
- 任务按可独立交付或验证的结果拆分，不为每个函数修改或操作步骤创建正式条目。
- 简要方案可以放在相关条目下；详细材料用链接。共享计划可链接于里程碑，局部计划链接于对应任务。
- 默认只勾选，不追加已完成工作说明。验证确有后续价值时，最多附一条短句，说明对象与结论，例如“验证：正常输入和单项失败场景均通过。”必要证据使用链接。
- 不写命令清单、终端日志、逐项测试结果、修复经过、长路径或哈希汇总。执行必要验证与保存验证过程是两件事。
- 验证属于完成条件而尚未完成时，任务不能勾选。全部条目勾选也不能代替对里程碑目标的判断；不得删弱完成条件制造完成。
- 不另建 STATUS、HANDOFF、会话摘要等重复状态入口。当前页面过期的内容应改写或移出，而不是追加新状态覆盖旧状态。

### Roadmap 模板

```markdown
# 路线图

## 已完成里程碑

- [单文件导出][completed]

## 当前里程碑

- [批量导出][current]

## 后续里程碑

### 发布准备

目标：交付可安装、可使用的版本。
完成条件：推荐安装与首次使用路径得到验证。

- [ ] 完成打包
- [ ] 核对公共使用说明

### 远期：多平台支持

预期结果：在其他目标平台运行。
依赖：先稳定当前平台的运行方式。

## Backlog

### 并行导出

价值：缩短大量输入的处理时间。
初步思路：先测量瓶颈，再决定是否引入并行。
待决问题：哪些工作适合并行？

[completed]: archive/milestone-2026-09-20-10-00-单文件导出.md
[current]: ../TODO.md
```

- 近期里程碑沿用 TODO 的目标、完成条件、任务和可选方案链接格式，启用时可以直接移动；远期不强求拆任务或填写日期。
- 已讨论的候选方案跟随 backlog 保存。写出了方案不等于承诺实施，也不等于允许 AI 开始工作。
- 将未来里程碑移入 TODO 时，roadmap 原处缩为当前入口链接，不保留第二份任务清单。进入实施前检查相关前提；仍成立时沿已有方案推进，有实质变化时说明差异，不无声重做方案。
- 当前 TODO 的“下一个里程碑”只保留名字与链接，不展开未来任务。没有明确下一项时省略该节。
- 已完成里程碑在 roadmap 中每项只留名称与链接，最新在前，不写结果摘要或测试数量。数量较多时按年份分组；不只链接混有 plan/spec 的归档目录。

### 完成、异常与归档

归档命名统一精确到分钟：

```text
plan-YYYY-MM-DD-HH-mm.md
spec-YYYY-MM-DD-HH-mm.md
milestone-YYYY-MM-DD-HH-mm-title.md
```

Plan/spec 使用创建时间，milestone 使用完成归档时间。移动时不改文件名；同名冲突不得覆盖已有材料。普通任务不强制分配 ID，文件和跨文档链接才需要稳定名称。

里程碑完成后，确认目标满足且未完成事项有明确去向，将 TODO 中该里程碑区块直接剪切到 `docs/archive/`；不重写、润色或另加阶段总结。相关 plan/spec 原文归档并修正引用，roadmap 增加历史链接，TODO 更新活动入口。下一里程碑是否开始，仍服从用户授权。

长期有效的约定在实施和计划内文档检查点维护到技术文档；不在归档时新增一次全面提炼、总结或证据整理任务。

- 暂停：保留未完成条目与方案，注明必要阻塞或恢复条件，不当作完成归档。
- 取消：明确写“已取消”和一句原因，不以 `[x]` 伪装完成。终止整个里程碑时可保存原清单，roadmap 单独标为已终止，不混入已完成列表。
- 拆分或延期：未完成内容移到明确的新任务、未来里程碑或 backlog，旧处保留必要去向。
- 共享 plan/spec：等相关工作全部结束再归档，不能因其中一个任务完成提前移动。
- 复杂里程碑的未来说明可以在内容确实需要时独立成文件，但任务状态仍只有一个维护位置；不因此要求每个里程碑预建独立文档。

## Plan/spec 与证据管理

Agent 自行选择 plan/spec 的结构与写法；插件不创建强制模板，不要求补全、改写、复核或持续维护其正文，也不强制每项工作都生成这些文件。

临时计划可以留在 agent 原生位置。作为 TODO 或 roadmap 长期依据的材料，需要保存到项目可持续访问的位置；不假设其他会话、机器或 agent 能访问原生临时路径。保存时不破坏 agent 仍在使用的原始材料，不反复导入同一份内容，并保留必要附件。

需要保存的 plan/spec 分别进入 `docs/plans/` 和 `docs/specs/`，由所属条目链接。相关实施工作结束后原文进入统一 archive，只处理移动、附件与链接，不加工内容。插件不要求计划作者因归档调整正文；迁移需要保证引用可用。

技术文档更新时，以代码和可验证行为说明实际实现，参考 spec 理解意图。实质差异应指出或成为待处理任务，不能把规格直接写成已实现事实，也不能借文档维护擅改源码。

`docs/evidence/` 只保存用户明确需要，或后续判断、测量、复现确实依赖的材料：

- 已有合适的持久来源时直接链接，不在 TODO、output 和 docs 重复存放同一份证据。
- 程序实际生成的模型、测量数据和测试产物与人工工作日志分开看待，必要原始产物可以保留。
- 不因保存产物就另写 Markdown 验证总结，不要求每个任务或里程碑都有 evidence。
- 重要已有证据不因任务完成就自动清理；人类决定、正式约束和未解决问题不能在整理时丢失。

## 技术文档：C4、源码导航与更新节点

### 内容与阅读路径

架构文档采用 C4，而不是自创一套平行层级；根据实际价值选择层次，不要求画满四层。

| C4 层级 | 回答的问题 |
| --- | --- |
| L1 系统上下文 | 服务谁，与哪些外部系统交互 |
| L2 容器 | 应用、进程和数据存储如何分工与通信；不等于 Docker 或源码目录 |
| L3 组件 | 一个运行单元内部，功能职责怎样划分与协作 |
| L4 代码 | 重要或复杂组件内部，由哪些类、接口、函数等实现 |

在组件附近补充目录和源码文件映射。读者应能从全局逐层深入，并在最深处找到自行维护的生产代码文件与关键运行脚本。辅助文件可按职责分组，文字不逐个长篇解释；测试按被测模块分组，生成或第三方代码说明用途和边界，不逐文件展开。

文件覆盖完整不等于绘制全部 import、调用或类关系。只展示有解释价值的关系，并说明图表达的是职责、调用、依赖或数据流，不能暗示未画出的依赖不存在。复杂运行机理按需使用 C4 动态图、时序图等说明输入输出、主要过程、关键算法思路和异常分支；公式推导、完整字段等进入确有需要的专题页。

以图为主，正文补充原因、约定和限制，不复述每个节点。每张图回答一个问题；层级和关系混乱或节点过密时拆图。纯目录层级可用短目录树，不强制画成图。

- 页面顶部链接上一级；总览图下按子系统提供深入阅读链接。
- 组件或子系统页链接局部实现地图，局部地图链接实际源码。
- 横向链接只用于理解真实协作，不做全页面互链。
- 小项目可以使用同一页的章节锚点，不为阅读层次预创建多批文件。

### 技术文档示例骨架

下面是架构总览的阅读顺序；组件页按实际问题展开，不要求每页填满所有标题。

```markdown
# 系统架构

已核对至：里程碑「批量导出」完成时。后续工作见 TODO。
返回：技术文档索引。

## 系统与外部环境

放置有实际信息的 C4 总览图，再用短文解释用途和边界。

## 主要部分如何协作

放置适用层级的关系图，并链接到相关组件说明。

## 关键运行过程

用动态图或时序图展示需要解释的流程，补充重要分支。

## 深入阅读

按职责链接组件、源码映射和必要专题；重要取舍链接 ADR。
```

`docs/tech/index.md` 按读者要理解的问题导航，不平铺全部历史文件。一个新页面应对应独立且需要展开的问题；不默认给每个模块或目录建文档。开发依赖面向开发者说明用途、关系和必要版本约束，不默认提供逐项安装教程。

### 图的格式与检查

Mermaid 是默认文本绘图方式，C4 决定表达的内容；不强制使用 Mermaid 的专用 C4 语法。节点标识稳定，标签与源码名称对应，箭头写清关系。使用适合实际阅读环境的语法，不为换绘图工具新增依赖。

只检查新增或改动的图：关系是否符合证据、是否可渲染、文字与连线是否清楚、范围和层间链接是否明确。优先使用已有渲染能力；没有时检查基础语法并说明未验证显示效果，不把人工阅读说成已经渲染。源码图保持可维护；图片可作为展示产物，不独立维护一份不同事实。

### 更新频率

Architecture 是最近一次核对过的架构快照，不宣称永远对应最新代码。每个里程碑末尾默认安排“核对并同步本里程碑影响的项目文档”：

- 在收尾或计划内检查点集中检查职责、边界、主要流程、接口、数据格式和关键约定，仅更新受影响部分。
- 无相关变化时确认后勾选，不为完成条目强行改文档。
- 发布时检查快照是否覆盖本次发布；已经覆盖就不重复更新。
- 普通任务完成不触发整套文档同步。较大里程碑可事先安排中途检查点；用户明确要求或过期说明会直接误导工作时，可提前修正。
- 开头标明核对到哪个里程碑或版本，后续工作链接 TODO；不另外维护逐任务的文档差异日志。
- 已实现与已发布需要区分。按适用范围说明事实，不把尚未发布但已经实现的结构长期写成未来目标。
- 更新时替换过期说明，不追加修改经过，不顺带重写无关章节或渲染未改动的图。

## ADR 与目录 README

ADR 保留现有三个同时成立的创建门槛：改变有明显成本、缺少背景容易误判、存在真实取舍。用户明确要求的决定记录按其范围处理。默认一至三句说明背景、决定和原因，必要时补充替代关系或影响，不强制长模板。

ADR 放在 `docs/adr/`，沿用 `0001-short-slug.md` 连续编号。已接受的决定保留当时语义，变化通过新 ADR 替代并互链；不随 milestone 归档，不另建 decisions。普通实施选择留在原 plan/spec，不因计划存在或阶段结束而提取 ADR。重要决定形成时记录，架构页链接原因而不复制全文。

目录 README 不默认创建。模块职责、目录结构和文件协作由技术文档维护，避免双份说明。独立发布的包或独立使用的工具可保留自身使用入口，必须就地看到的生成说明和操作限制也可保留；其他详细内容使用链接。已有重复 README 只在明确的文档整理范围内合并，不借普通开发清理全仓库。

## README：初学用户的使用入口

面向不熟悉仓库、代码经验较少的预期用户。沿用项目语言约定；新项目默认英文根 README，正式中文版本按已确认路径维护，中文入口放在最前面的徽章行，中文页提供反向语言入口。创建或实质重写时，默认补齐中文入口需要的正式翻译；用户明确选择单语时服从其要求，孤立小改不因此扩张为翻译任务。正式翻译保持章节结构与公共事实一致，表达自然，不要求逐句对应。

### 顶部徽章

- 徽章统一放在 `<p align="center">` 的 HTML 行中，每项使用带链接的 `<img>`；HTML 查询参数使用 `&amp;`。
- 统一使用 Shields.io 的 `style=for-the-badge`；优先使用对应的真实 logo，可用 `logoColor` 保持对比度。没有合适 logo 时不使用误导性的图标。
- 默认必备项为中文 README 入口和许可证。语言徽章链接正式译文，许可证徽章链接真实许可证文件；缺少许可证时向用户确认，不为了徽章擅自选择许可证。不得生成死链接或虚构状态。
- Platform、release、运行时版本、安装入口等按项目实际选择。徽章不能把某次测试环境写成最低要求，或把计划支持的平台写成已支持。
- 中文入口在前，随后是许可证和有用的项目徽章。徽章只出现于顶部，末尾不重复。
- 顶部许可证徽章已经清楚表达并链接许可证时，不默认再写“许可证”章节；确有额外授权或署名说明时才保留必要文字。

### 内容取舍与更新

- 获取方式由项目决定：发行版、插件市场、包管理器、命令安装或源码获取均可，不强制 clone 或 ZIP。不把未来分发计划写成已有能力。
- 有多个路径时先推荐一个，再按用户环境提供必要分支；修改文件、运行命令和成功信号都按项目实际选择。
- 使用环境与开发环境分开。能合理提供获取方式的依赖给出合适的官方入口；需要用户自行准备的商业软件说明兼容版本和可用条件，不猜测安装过程。关键获取方式或兼容范围不明时再提问。
- 开发依赖、转换机制、维护命令等进入技术文档，贡献章节提供导航，不在 README 重复开发环境安装教程。
- 命令和路径来自项目或可靠资料；能执行的相关验证按实际范围完成，不能验证时说明限制，不编造结果。
- 里程碑收尾与发布检查点核对受影响的能力、环境和使用路径；没有变化不改正文。已经失效的安装命令或入口及时修复，不等待阶段结束。
- 移除“实质修改默认先提交审计并等待确认”的门槛。已授权修改直接执行；只有读者、定位或推荐路径等关键歧义才询问。用户要求审查时保持只读，不为每次更新额外生成审计报告。
- README 中可以维护简短贡献章节，不默认创建完整 CONTRIBUTING 或维护手册。使用路径清楚后停止，不把项目全部知识集中到 README。

## 使用说明：完成具体用户任务

由 `project-docs-readme` 负责，与 README 一样面向初学用户。README 帮助用户判断是否适用并首次成功；使用说明回答日常怎样操作；`docs/tech/` 解释程序为什么这样运行、代码怎样组织。三者互相链接，不复制正文。

当快速开始之外确有多种常见任务、选项或需要展开的操作时，默认创建 `docs/usage.md`；简单项目无需单独创建。内容变多后按独立用户任务拆分，并保持一个使用入口，不因每项功能或每次发布新增手册。

使用说明与 README 一起在里程碑或发布检查点核对，只更新受影响用法和正式翻译；已经失效、会直接阻碍用户操作的步骤及时修正。改写旧步骤，不追加版本工作日志，不生成独立使用说明验收报告。相关可执行验证依任务条件进行，无法验证的内容不声称已经运行成功。

## AGENTS 与指导规则

沿用薄入口：相关文档路由、必要工作流触发器和真实项目约束。AGENTS 只指向规划与技术文档，不复制完整模板、生命周期、架构或验收说明。局部规则只在有实际需要时放到适用目录，不要求每个目录都有指导文件。

创建或整理项目指导文件时，以 `AGENTS.md` 为唯一正文，`CLAUDE.md` 使用指向它的相对软链，不维护两份内容。已有独立 `CLAUDE.md` 时，先处理其中仍有效且未被 AGENTS 覆盖的项目规则，再替换成软链，不能直接覆盖丢失约定。适用的目录级指导采用同样方式，无独立规则的目录不为软链额外创建文件。检查链接目标和循环即可，不因此安排 Claude 运行验证。

Guidance 技能应将最初审查的原则用于筛选规则，而不是把整套审查清单塞进每个项目：

- 明确适用任务与条件，不用“任何修改都必须”包办所有场景。
- 按任务读取最小相关材料，不要求微小改动前通读仓库或重复读取未变化的上下文。
- 保留有真实顺序依赖的步骤，其他执行细节交给 AI 判断。
- 保留项目需要的验证，不无条件要求重复核查，也不能仅因涉及测试就判为过时。
- 已授权范围内继续，避免反复请求批准；提问只针对真实缺失的决定或明确边界。
- 详细主题只有一处维护；全局与局部规则不重复。

明确、稳定的语言、记录强度、提交方式等用户约定不能仅因属于个人偏好而删除。目录作用域遵循实际工具行为，不把其他平台规则套用到 Codex。此次只检查 Codex，不扩展其他平台验证或用户全局配置维护。

## 共享写作规则

在 project-docs 插件内维护一份短的共同写作规范，供七个技能使用；不另增自动写作技能。各技能只补充针对自己读者的差异，模板和较长正反例按需加载，同轮已经读取的内容不重复读取。

这项设计调整了旧版“每个技能完全自包含、不得有运行时共享 reference”的选择。实施时需同步相关仓库规则，并确保共同资料随插件分发、路径可访问，不依赖仓库外部或兄弟插件。共同规则保存在 `project-docs-progress/references/writing-style.md`，其余六技能通过插件内相对链接读取，不复制正文。

共同要求：

- 标题简明概括，正文说清动作、对象和结果。一个句子围绕一个主要意思。
- 使用具体动词，不用“闭环、收敛、对齐”等抽象表达代替实际信息。
- 术语保留准确含义，按读者背景解释，不把多个技术名词压成难读短语。
- 进度先说明结果，必要证据另链接；不把完成情况、验证、历史和下一步塞进一句话。
- 不为显得完整重复内容；简化语言不能把已实现写成已发布，或把局部验证写成全面通过。

| 场景 | 写法 |
| --- | --- |
| README | 最严格地面向初学用户，说明必要概念和具体操作 |
| 使用说明 | 按用户任务写清条件、操作、结果和选项影响，不堆内部机制 |
| Milestone 标题 | 简短明确，例如“批量导出与故障隔离” |
| TODO 条目 | 具体结果，例如“单个文件导出失败后继续处理其他文件，并列出失败原因” |
| 技术正文 | 图在前，用具体过程解释机理，必要术语不省略 |
| ADR | 简短说明背景、选择和原因 |
| AGENTS | 条件、动作、边界可以紧凑，但不压缩到产生歧义 |
| 工作说明与最终回复 | 直接说明完成了什么、验证了什么、还缺什么，不堆术语 |

例如，“完成规划权威来源收敛及活动状态同步”应写成“任务状态统一维护在 TODO，其他文档只保留链接”。

风格规则直接指导插件编写的文档和调用技能时的协作表达，不新增逐句写作审查、报告或额外总结步骤。它不触发原样保存的 plan/spec 或历史材料重写，也不宣称在技能未加载时改变所有 agent 的全局表达。

## 旧项目迁移

只改插件不能消除项目内已有的追加记录规则。迁移时同步考虑 TODO、AGENTS、方案、索引和技术说明的实际约定，保护未完成事项、未来方案、人类决定、长期约束和必要证据。

用户可选择：

- 轻量迁移（默认）：整理当前入口与未来工作，历史保留原貌，必要时移动和修复链接。
- 完整整理：同时按新格式整理历史材料，保留原有事实、决定和必要证据。

用户已明确要求或选定范围时直接执行，不重复提问。范围不明确且选择会明显改变工作量或历史内容时，先给出上述选项。局部修改只检查目标、相关权威材料与受影响引用；确有跨文档迁移时才扩大盘点，不能每次完整扫描仓库。

AutoBlade 等已有项目需要另行迁移，本次实施不改动其他仓库。反对重复叙述不意味着删除用户要求的测量、判断依据或原始产物。

## 实施边界与轻量验收

实施时更新七个技能、所需模板与引用、Codex 调用设置，以及受影响的 catalog 和公开入口。保留插件内单一技能来源，不手改生成镜像；新增共享资源需要同步旧的自包含规则。版本与正式发布按届时范围处理，本设计不虚构已发布版本，也不执行安装晋级。

验收遵循[项目轻量验收规则](../SKILL_RULE_GUIDELINES.md#技能内容的轻量验收)：

- AI 根据已确认需求审阅指令、模板和边界，不为每条规则编写测试，不生成额外行为或写作审查报告。
- 检查 Codex 的技能发现、调用配置和模板、共享规则的可访问性。内容合理不能代替安装与资源检查。
- 不默认要求第二个真实仓库、模型调用或完整任务模拟；实际行为通过后续使用反馈调整，用户明确要求时再做行为验证。
- 交付时区分已执行检查与预期行为。历史 2.0 验证不能证明新方案的运行效果。
- 脚本或安装逻辑实际发生变化时，执行相关检查；正式发布仍遵循声明的发布范围。本次不安排其他平台验证，也不借此删除现有平台支持。

内容审阅要能确认：普通任务不会默认生成报告；未来方案可找到；里程碑历史主要由原文移动形成；技术文档按节点更新且能逐层阅读。这些是设计与使用反馈的判断标准，不是要求额外运行一套行为测试。
