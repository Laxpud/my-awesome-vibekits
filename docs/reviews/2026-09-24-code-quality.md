# code-quality 技能审查记录

记录日期：2026-09-24

来源：上轮只读审查。本文仅记录问题，未实施修复。

说明：没有“模型升级使指令失效”的实证；以下问题依据当前指令的范围、分层和执行效果记录。

## A1：注释细则缺少按需加载分层

- 主要类别：二、缺少按需加载的分层结构
- 原文与位置：[`SKILL.md`](../../plugins/code-quality/skills/code-comment-standard/SKILL.md) 第 46-313 行依次包含“分层级注释执行规范”“主流编程语言专属规范”“绝对禁止行为清单”“注释质量自检标准”“特殊场景处理规则”。该技能目录没有配套 `references/` 文件。
- 原有目的（推断）：在一个入口中覆盖不同注释层级、语言和场景，避免遗漏规则。
- 问题：323 行主文件同时承载多个相对独立的工作流程，触发技能时会加载与当前任务无关的大量规则，主入口也难以准确表达按需范围。
- 已有建议方向：保留主文件中的触发范围、共同底线和路由；将文件头与符号文档、逻辑注释与标签、较长示例及特殊场景拆到按需 reference，避免拆成大量细碎文件。
- 保留边界：不得删除“保持代码行为、遵循项目既有风格、避免错误或敏感信息”等共同约束；只是调整详细规则的加载位置。

## A2：注释任务要求无边界的完整阅读

- 主要类别：三、操作步骤过于僵化
- 原文与位置：[`SKILL.md`](../../plugins/code-quality/skills/code-comment-standard/SKILL.md) 第 40 行：`必须先完整通读代码，拆解代码的整体功能、模块划分、核心逻辑、输入输出、依赖关系、异常处理、边界条件，完全理解代码语义后，再生成注释`。
- 原有目的（推断）：防止断章取义和错误注释，确保注释确实匹配代码语义。
- 问题：对每次注释任务都要求完整分析所有维度，没有按目标文件、改动范围和实际语义依赖裁剪；小范围审查也会被迫执行固定的全量阅读流程。
- 已有建议方向：改为先阅读目标代码及其必要的调用、类型、配置和既有注释上下文；仅在语义依赖需要时扩大阅读范围。
- 保留边界：保留“先理解后注释”和不得编造代码语义的原则，不将其改成无需理解代码即可修改注释。

## A3：添加文件头未明确沿用已有授权

- 主要类别：六、过度谨慎的请示与审批措辞
- 原文与位置：[`SKILL.md`](../../plugins/code-quality/skills/code-comment-standard/SKILL.md) 第 54 行：`为代码文件添加文件头注释之前，必须主动询问用户是否需要`；第 91 行再次规定：`禁止在未询问用户的情况下为所有文件自动添加文件头注释`。
- 原有目的（推断）：防止在用户未要求时批量添加文件头，避免扩大修改范围和制造无价值元数据。
- 问题：“必须主动询问”没有明确排除用户已经授权添加文件头的情况，容易把授权要求变成重复问答。
- 已有建议方向：只在用户意图、文件范围或批量影响不明确时询问；用户已经明确授权时直接执行。保留普通业务文件不默认添加文件头的范围判断。
- 保留边界：不因删除重复请示而放宽“普通业务文件、工具函数文件和配置文件不应自动添加文件头”的适用范围，也不放宽作者、日期等信息不得凭空捏造的要求。

固定契约和既有规范仍保留：代码行为不变、既有注释风格优先、公共接口应说明真实契约、不得写入敏感信息，以及按语言和项目规范输出。
