### 语言与注释

- 代码标识符、模块名、CLI 命令、终端输出、日志消息、异常消息和配置键默认使用英文。
- 新增或编辑解释性注释、docstring、TODO、维护者说明和复杂逻辑说明时，默认使用中文，除非项目规则另有要求。
- 注释面向未来维护者和新手读者，目标是帮助读者理解代码背后的领域语义、数据契约、流程约定、边界条件、核心算法、配置语义、设计取舍和隐含假设；避免逐行复述代码语法。
- 对复杂代码要主动写维护型注释，注释密度可以明显高于普通业务代码；不要因为代码“能跑”就省略关键说明。
- 以下场景必须补充注释：
  - 领域规则、业务规则、数学/物理模型、协议约定或工程近似；
  - 数据结构、schema、数组 shape、字段含义、单位、坐标系、状态含义；
  - 跨模块接口、外部系统交互、配置项语义、输入输出契约；
  - 并发、缓存、事务、重试、降级、边界条件和异常分支；
  - 迁移旧代码、兼容历史行为、复刻论文/规范/第三方系统逻辑；
  - 临时假设、尚未验证的选择、未来需要修正的 TODO。
- 核心流程、复杂算法和容易误解的实现应使用编号步骤注释，帮助读者沿着业务、数据或数学流程阅读。
- 公共 API 使用当前语言或框架的标准文档注释格式；内部复杂逻辑使用块注释说明关键意图、数据流和约束。
- 英文只保留代码标识符、公式符号、shape、单位、配置键、日志/异常文本、协议字段和生态惯例。
- 新增或大幅修改复杂代码时，同步补充必要的文件级说明、公共 API 说明和关键块级注释，避免留下“代码能跑但读不懂”的实现。

### Git 偏好

- 只在我明确要求时才提交本轮相关改动。
- 提交前只暂存本轮相关文件，不要混入生成物、缓存、虚拟环境、本地测试输出或无关工作区改动。
- 提交信息默认使用 Conventional Commits，scope 具体，summary 清晰；语言默认使用中文。
- 非简单改动在提交正文中用独立换行的 bullet 概括主要改动、验证方式和迁移说明。
